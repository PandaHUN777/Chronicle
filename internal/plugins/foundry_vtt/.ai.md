# foundry_vtt Sub-Plugin

The `foundry_vtt` plugin is the Foundry-VTT-specific extension to the
generic `packages` plugin. Every Foundry assumption Chronicle used to
make natively now lives here: per-campaign signed manifest URLs,
per-campaign pinning, the `chronicle-package.json` descriptor reader,
and the post-install `module.json` version rewrite that keeps Foundry's
reported version in sync with what was actually installed.

The `packages` plugin remains generic — zero Foundry-specific code
in `packages/`. This plugin is the only place strings like
`"manifest"`, `"download"`, `"module.json"`, and
`"chronicle-package.json"` appear in the Chronicle backend.

## Why this plugin exists

The operator's directive, verbatim: *"This should be very modular and
basically the foundry package would instruct these processes, not
baked in directly to chronicle. We don't want foundry stuff inside
chronicle natively, because then that just makes a redundant mess."*

This sub-plugin owns ALL Foundry-specific behavior; `packages` owns
generic external-repo management. The boundary is the
`packages.PostInstallHook` extension point.

## Modularity contract

**This plugin is INERT when no foundry-module typed package is
registered in the `packages` catalog.** The routes mount
unconditionally at boot, but:

- The owner tab fragment renders an empty state ("ask an admin to
  register the module").
- The public manifest endpoint returns a categorized 503 with
  `code=no_package_registered` and an actionable message.
- The `PostInstallHook` is registered but never fires (no
  foundry-module installs to fire on).

Removing the Chronicle-Foundry-Module package from `/admin/packages`
turns this plugin off. There's nothing else to configure.

## Architectural decisions

### Why a sub-plugin and not a `packages` extension

**Decision**: `foundry_vtt` is a sibling plugin to `packages`, communicating
via the `PostInstallHook` interface and the `PackageReader` adapter, rather
than extending `packages` directly with Foundry-aware methods — the
operator explicitly disallowed baking Foundry logic into the generic
plugin. Future TTRPG VTT extensions (Roll20, Owlbear) follow the same
pattern.

### Why descriptor-driven (and not hardcoded)

**Decision**: The post-install hook reads `chronicle-package.json` from the
extracted install dir — it declares the manifest path, which fields to
rewrite, and the endpoint URL templates — rather than hardcoding every
Foundry assumption in Chronicle. Hardcoded defaults (`defaultDescriptor()`)
apply when no descriptor is present, so a module zip without one still
works. A present-but-invalid descriptor fails the install loudly rather
than silently falling back, so upstream packaging bugs surface immediately
instead of being masked.

### loadDescriptor canonical-vs-fallback pin

The fallback `defaultDescriptor()` values (`descriptor.go:142-156`) MUST match
what the canonical `chronicle-package.json` ships from
`chronicle-foundry-module`, or an install WITH a descriptor would behave
differently from an install WITHOUT one, defeating the descriptor's purpose.
`descriptor_fallback_test.go` + `testdata/chronicle-package.json` pin this
alignment as a committed snapshot (per-field assertions; `package.id`
excluded, since it's descriptor-required and intentionally empty in
defaults). The snapshot is not a live fetch — regenerate it by hand whenever
`chronicle-foundry-module`'s canonical descriptor changes; its
`tools/check-package-descriptor.mjs` reminds maintainers.

### Why tokens live in a separate table (not CampaignSettings JSON)

**Decision**: `foundry_vtt_campaign_tokens` is a dedicated table with
`(campaign_id, token_version, rotated_at)`, separate from
`CampaignSettings.FoundryModulePin` (owned by the campaigns plugin). Token
rotation is a `foundry_vtt`-owned operation; keeping it in its own table
avoids needing a campaigns-plugin write path for it.

### Inline-IIFE onclick handlers (standing rule)

Every onclick handler inside an HTMX-swapped fragment in this plugin
(`admin.templ`, `owner_tab.templ`, `autopin_banner.templ`) uses an INLINE
IIFE in the attribute value, built in Go as a string in
`onclick_handlers.go`, wrapped in a `templ.ComponentScript` with an empty
`Function` (no `<script>` tag) and the body in `Call`. Templ writes `Call`
directly into the `onclick="..."` attribute.

**Never use templ `script` helpers in an HTMX-loaded fragment.** They emit
`<script>function __templ_X(){...}</script>` alongside a button whose
onclick references `__templ_X(...)` by name. Browsers do not reliably
execute an innerHTML-swapped `<script>` tag synchronously with the
surrounding HTML, so the button can be clicked before the function is
defined:

```
Uncaught ReferenceError: __templ_X is not defined
```

The inline-IIFE pattern instead wraps the JS body in `(function(){...})()`,
uses single-quoted JS strings throughout (double quotes would close the
outer `onclick="..."`, since templ doesn't HTML-escape `Call`), and
JS-escapes interpolated values via `text/template.JSEscapeString` so
embedded apostrophes/backslashes can't break out.

**Contract tests** in `onclick_handlers_test.go` assert every handler (a)
starts with `(function(`, (b) contains no literal `"`, (c) contains no
`__templ_` substring.

### HTMX-swap-safe pattern requirements (standing rules)

Every interactive element in an HTMX-swappable fragment in this plugin
follows these rules:

1. **Inline `onclick="(function(){...})()"` IIFEs** — not
   `document.addEventListener`/delegated listeners, not templ `script`
   helpers (see above).
2. **Inline literal Alpine `x-data="{ open: false }"`** — never
   `x-data="someExternalFunction()"`. An external reference can be
   undefined when Alpine processes the directive right after an HTMX swap.
3. **`<details>` + `<summary>` for collapsible sections** when JS isn't
   needed for the toggle. Browser-native, zero race window. Combine with
   `hx-trigger="toggle once from:closest details"` for lazy-load on expand.
4. **Defense-in-depth `style="display:none"`** alongside `x-show=open` for
   modal-like reveals, to prevent a flash if `x-cloak` evaluation runs late.

### Coordinator-level pre-merge rules

Three checks apply to every PR touching this plugin's fragments:

1. **Fragment consumer trace**: a PR creating a fragment served via hx-get
   lists every consumer (the templ files that embed it); a PR deleting a
   fragment endpoint verifies every consumer was updated to consume
   something else.
2. **On-disk artifact trace**: a PR changing how a URL gets served verifies
   the on-disk artifact (extracted zip's `module.json`, cached files, etc.)
   carries the new URL — Foundry reads the on-disk file after install, not
   just what the manifest endpoint serves on first fetch.
3. **HTMX click-handler trace**: a PR adding interactive elements to an
   HTMX-loaded fragment verifies the click handler is an inline IIFE, not a
   templ `script` helper or a delegated listener.

These are also encoded as contract tests where applicable
(`onclick_handlers_test.go`, `zip_rewrite_test.go`, `auto_pin_test.go`).

### Per-campaign zip rewriting at download time

**Decision**: The download endpoint streams a zip with the embedded
`module.json` REWRITTEN to carry per-campaign Chronicle URLs, on every
request — no caching. Per-campaign URLs require per-campaign zips (a single
cached zip can't carry different URLs for different campaigns), and Foundry
reads the on-disk `module.json` after extraction as its source of truth for
update-check URLs, so serve-time manifest rewriting alone is not enough —
the file on disk has to carry Chronicle URLs from the first install onward.
Re-zipping per request is cheap: modules are small (<5 MB) and installs are
infrequent.

The manifest endpoint and download endpoint share `resolveCampaignManifest`
as their single source of truth for descriptor loading + URL rewriting, so
both produce identical rewritten bytes for the same `(campaign_id,
token_version)` pair.

### Auto-pin-on-install (vs. silent forward-bump)

**Decision**: After every foundry-module install, every campaign with an
empty pin (auto-tracking) gets explicit-pinned to the PREVIOUS version,
rather than silently following the newly-installed version. The admin sees
the version spread via the "Campaigns Using vX.Y.Z" UI and decides
per-campaign whether to bump — this avoids an install silently moving every
auto-tracking campaign forward with no notification, while also not
blocking the install itself on admin confirmation. The admin "Force-update
All Older" mass action moves every older-pinned campaign to the latest in
one click when that's what's wanted.

A one-time bootstrap migration pins every pre-existing auto-tracking
campaign to the foundry-module's currently-installed version at first boot
after this shipped. Idempotency: the version it pinned to is stored under
`foundry_vtt.autopin_migration_completed_for_version` in `site_settings`;
subsequent boots read that key and skip. Clearing the key re-triggers the
migration (an intentional escape hatch). No-op (and does not set the flag,
so the next boot retries) when no foundry-module package is registered yet
or it has no installed version.

## Database tables

### `foundry_vtt_campaign_tokens`

```
campaign_id   CHAR(36)  NOT NULL  PRIMARY KEY
token_version INT       NOT NULL  DEFAULT 1
rotated_at    TIMESTAMP NOT NULL  DEFAULT CURRENT_TIMESTAMP
FOREIGN KEY (campaign_id) REFERENCES campaigns(id) ON DELETE CASCADE
```

`token_version` is the rotation counter. Sign payload =
`HMAC(secret, "foundry-vtt:{campaign_id}:{token_version}")`. Rotate =
increment counter, every previously-signed URL becomes invalid on
next manifest request.

Renamed from `foundry_module_campaign_tokens` by migration 001, which
also drops the orphaned `foundry_module_versions` table. See "Fresh-database
bootstrap" below for why migration 001 alone cannot bring up a fresh
database, and what migration 002 + the reconciler do about it.

## Extension point: PostInstallHook

`foundry_vtt.NewPostInstallHook()` returns a struct satisfying
`packages.PostInstallHook`, registered at boot via
`packages.RegisterPostInstallHook(pkgService, hook)`.

Fires after every `PackageTypeFoundryModule` install:

1. Loads `chronicle-package.json` from the install dir (or applies
   defaults).
2. Reads `module.json` at the descriptor-declared `moduleJsonPath`.
3. Overwrites the `version` field with the installed version
   string.
4. Writes the file back.

Errors fail the install loudly. The packages plugin's `InstallVersion`
cleans up `destDir` on hook failure, so a retry installs from scratch.

## Extension point: chronicle-package.json descriptor

The schema is owned on the Foundry side
(`keyxmakerx/Chronicle-Foundry-Module#35`). Chronicle's adoption is
described here.

### Schema v1 (canonical)

```jsonc
{
  "schemaVersion": 1,
  "package": {
    "id": "chronicle-sync",
    "kind": "foundry-module",
    "moduleJsonPath": "module.json"
  },
  "serving": {
    "rewriteFields": ["manifest", "download"],
    "manifestEndpoint": "/api/v1/campaigns/{campaign_id}/foundry-vtt/module.json?token={token}",
    "downloadEndpoint": "/api/v1/campaigns/{campaign_id}/foundry-vtt/module.zip?token={token}",
    "perCampaignSignedToken": true,
    "zipContentRoot": ""
  }
}
```

### Fallback semantics

When no `chronicle-package.json` exists in the install dir,
`defaultDescriptor()` applies. The defaults match the canonical schema
above — equivalent to what the Foundry module's published descriptor
declares. This means a module zip without a descriptor still works: it
uses the fallback, while a zip that ships one drives behavior from it.

### Schema versioning

`schemaVersion` is the load-bearing field. The hook recognizes
only `currentSchemaVersion` (1 today). Unknown major versions
fail the install loudly. Future v2+ requires coordinated Foundry +
Chronicle releases.

Within v1: missing optional fields fall back to defaults via
`applyDefaults()`. Modules can ship minimal descriptors (just
`schemaVersion` + `package.id`) and inherit everything else.

## Error handling contract

Every public-facing error follows this format:

```
<what failed>: <technical detail>. <likely cause>. <actionable next step>.
```

See `errors.go` for all pre-defined constructors. Examples:

<!-- foundry-vtt-error-catalog-start -->
| Constructor | Category | HTTP Status | Format-compliant Message |
|---|---|---|---|
| `ErrInvalidToken` | auth | 403 | Wrong HMAC or rotated → operator rotates URL via campaign settings. |
| `ErrNoPackageRegistered` | config | 503 | No foundry-module package → admin adds it via `/admin/packages`. |
| `ErrPinnedVersionNotInstalled` | config | 503 | Pin to missing version → admin installs OR owner changes pin. |
| `ErrNoVersionAvailable` | config | 503 | Package exists, no version installed → admin clicks Install. |
| `ErrTokenNotInitialized` | config | 503 | First-time campaign hit before owner visited settings → owner opens VTT Setup Guides. |
| `ErrDescriptorInvalid` | validation | 422 | Bad descriptor in zip → fix upstream OR remove descriptor for defaults. |
| `ErrModuleJSONMissing` | internal | 500 | Zip malformed → admin retries OR upstream fix. |
| `ErrCampaignNotFound` | not_found | 404 | URL refers to deleted/wrong-instance campaign → owner mints a fresh URL. |
| `ErrInternal` | internal | 500 | Server-side fault; code is dynamic. Wildcard constructor; logged with the wrapped cause. |
<!-- foundry-vtt-error-catalog-end -->

JSON shape returned to public endpoints (Foundry's `update-info.mjs`
consumes this):

```json
{
  "error": "<code>",
  "message": "<format-compliant message>",
  "category": "<config|auth|not_found|validation|internal>"
}
```

### Adding a new error code

The catalog above is mechanically checked against `errors.go` by the tests
in `errors_test.go`. Three coupled sources must stay in sync; the tests fail
loudly with an actionable message if any pair drifts. Workflow:

1. **Add the constructor to `errors.go`** following the existing
   four-clause Message format. Pattern:

   ```go
   func ErrSomething(...) *Error {
       return &Error{
           Category: ErrCategoryConfig, // or ErrCategoryAuth, etc.
           Code:     "some_unique_snake_case_code",
           Message: "<what failed>: <technical detail>. " +
               "<likely cause>. <actionable next step>.",
       }
   }
   ```

2. **Add a row to the catalog table** above (inside the
   `<!-- foundry-vtt-error-catalog-start -->` /
   `<!-- foundry-vtt-error-catalog-end -->` markers) with the
   constructor name, category, HTTP status, and a one-line
   message summary. The HTTP status is derived from the category;
   the test enforces the mapping.

3. **Run `make foundry-error-catalog`** from the repo root to
   regenerate `error-catalog.json`. Commit the regenerated file.

4. **Run `go test ./internal/plugins/foundry_vtt/...`** —
   `TestErrorCatalog_*` will pass when all three files agree;
   they fail with a precise diff message until then.

Foundry's `update-info.mjs` reads `category` and `message` from Chronicle's
response directly, so adding new codes needs zero Foundry deploy.

### Drift guard scope

The drift guard mechanically aligns three sources:

- `errors.go` — typed constructors (source of truth for Code + Category)
- `.ai.md` — human-authored catalog table (consumer-facing docs)
- `error-catalog.json` — machine-readable artifact (consumed by
  Foundry-side docs)

The shared parser lives in `errors_catalog.go` and is used by both
the test path (`errors_test.go`) and the regeneration path
(`cmd/foundry-error-catalog/main.go`). The canonical catalog also publishes
at `/internal/plugins/foundry_vtt/error-catalog.json`; Foundry's repo
references this artifact in its own docs (`.ai.md` and `API-CONTRACT.md`).

### Standing pre-merge rule

**Catalog drift trace** — every PR touching `errors.go` (adding, removing,
or modifying constructors) must also update the `.ai.md` catalog table
inside the markers AND regenerate `error-catalog.json` via
`make foundry-error-catalog`. The drift tests enforce this mechanically.

This sits alongside the coordinator-level pre-merge rules above (fragment
consumer trace, on-disk artifact trace, HTMX click-handler trace) — four
mechanical safeguards against the "forgotten consumer / wrong contract /
silent regression" class of bug this plugin is prone to, given how much of
it lives in HTMX-swapped fragments and cross-plugin extension points.

## Fresh-database bootstrap — read before touching migrations

**This plugin's migration `001` cannot run on a fresh database and never
will.** It is a consolidation migration (`RENAME TABLE
foundry_module_campaign_tokens TO foundry_vtt_campaign_tokens`) whose source
table is created by a plugin that no longer exists. On a genuinely fresh
install there is no source table to rename, so `001` fails — and the plugin
migration runner returns on the first failed migration, so every migration
after `001` (including any future one) would be unreachable too.

The repair has two halves, and **neither edits `001`** (migrations are
append-only, `tools/check-migration-immutability.sh`):

- **`reconcile_consolidation.go` → `ReconcileConsolidationState`** records
  `001` as applied on any database where its RENAME has **no source
  table**. It runs next to `PreMigrationCheck` in `cmd/server/main.go`,
  before the plugin schema pass.
- **Migration `002_ensure_campaign_tokens`** states the post-consolidation
  shape in idempotent DDL (`CREATE TABLE IF NOT EXISTS` /
  `ADD COLUMN IF NOT EXISTS`).

**A database that still HAS `foundry_module_campaign_tokens` is
untouched** — the reconciler does not fire, `001` runs for real, and its
live token rows are carried across. Fresh install, completed upgrade, and
an upgrade that died between `001`'s two statements all converge on the
same schema.

`make test-freshdb` / `cmd/server/freshdb_migration_test.go` replay the real
bootstrap against genuinely empty MariaDB schemas — one from zero, one from
the pre-consolidation shape — in CI, and fail if either test merely skips
rather than running (a silent skip is exactly how this defect went
