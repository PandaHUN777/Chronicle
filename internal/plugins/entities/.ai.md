# Entities Plugin

<!-- Core plugin -- always enabled, cannot be disabled. -->

## Purpose

Core plugin, always enabled. The heart of Chronicle: universal entity system
with configurable types, dynamic fields, full-text search, nesting, and a
rich profile page.

## Critical footgun

All `entity_types` SELECT queries MUST route through `entityTypeColumns` const + `scanEntityType(rowScanner)` helper in `repository.go`. Never add a bespoke SELECT/Scan in a single method. `TestEntityTypeRepository_Integration` is the live-DB guard.

Plugin (Core -- always enabled)

## Domain Concepts

- **Entity:** A worldbuilding object with a name, type, rich text entry,
  and configurable fields. Everything is an entity.
- **Entity Type:** A configurable template defining what fields an entity
  has. Per-campaign. Defaults ship pre-configured (Character, Location, etc.)
  but can be customized by the GM.
- **Fields Definition:** JSON array on entity_types defining field key, label,
  type, options, and display section.
- **Fields Data:** JSON object on an entity storing that entity's values for
  its type's fields.
- **Entry:** The rich text body of an entity (TipTap/ProseMirror JSON).
- **Player Notes:** Separate player-facing content (`player_notes` JSON +
  `player_notes_html` HTML). Distinct from the main entry (DM content). Maps to
  a second Foundry Journal page.
- **Privacy:** `is_private` flag makes an entity visible only to Scribes and Owners.
  Players see 404 for private entities. Owned end-to-end by the slide-in
  permissions card (`static/js/widgets/permissions.js`); the entity edit
  form and the inline metadata panel do not carry an `is_private` input —
  the card writes via `PUT /entities/:eid/permissions`. `UpdateEntityInput.IsPrivate`
  is `*bool` so the form/metadata handlers can pass `nil` and have the
  service preserve the entity's existing value. The wire (syncapi) side of
  this is also `patch.Field[bool]` — a value-typed `bool` there let a
  Foundry actor-sync `{name}`-only rename push bind `false` and publish a
  hidden character entity to every player; its batch twin `syncChange` is
  the same type.

### `Update` is a PARTIAL update

| what the caller sends | what happens to the stored value |
|---|---|
| field **absent** (`patch.Field` zero / `IsPrivate == nil`) | preserved |
| field present with a **value** | replaced |
| field present and **explicitly `null`** (or `""` on `type_label` / `parent_id`) | cleared |

`Name`, `TypeLabel`, `ParentID` and `Entry` are `patch.Field[string]`;
`IsPrivate` stays `*bool` (a NOT NULL column has no cleared state, so
nil-preserve already IS the three-state contract). `ParentID` used to be a
plain string where `""` meant "clear", and syncapi's update body had no
`parent_id` member at all, so every sync push detached the entity from the
hierarchy — as did every AI-workspace commit-update. Pinned by
`entity_partial_update_test.go` and `syncapi/entity_partial_update_test.go`
in all three directions.

`Entry` keeps a legacy `""`-means-preserve reading (no client can blank a
body through this input); an explicit null does clear it. `ImagePath` is
inert — the service never reads it, so campaign import silently drops image
paths (a named exception in `internal/patch/partial_update_contract_test.go`).

- **Field-level visibility (`gm_fields.go`):** two tiers, orthogonal to the
  whole-entity privacy above and to each other. `FieldDefinition.GMOnly`
  hides a field's VALUE from every Player-tier viewer, including the entity's
  own claimed owner — a true GM secret (e.g. Draw Steel's `gm_notes`/director
  notes). `FieldDefinition.OwnerOnly` hides a field's VALUE from every viewer
  except GM-tier roles AND the entity's own claimed owner (`Entity.IsOwnedBy`)
  — for content that's private to one player but not a GM secret (e.g. Draw
  Steel's `backstory`, so a claimed player character stays party-visible on
  the Cast roster without leaking that one field to teammates). Both are
  declared via a system manifest's `gm_only`/`owner_only` field annotation,
  applied to new types at preset time, and converged onto existing types by
  `EntityService.SyncFieldGMFlags`/`SyncFieldOwnerOnlyFlags`
  (`internal/app/preset_applier.go`'s
  `reconcileFieldGMFlags`/`reconcileFieldOwnerOnlyFlags`, run at boot and on
  package install/update). `FilterRestrictedFields` (composes
  `FilterGMOnlyFields` + `FilterOwnerOnlyFields`) is the one call every
  fields_data egress point uses: entities-plugin `GetFieldsAPI`/`PreviewAPI`,
  `CharacterSurfaceSchemaJSON`, and syncapi's `GetEntity`/`ListEntities` (the
  same path Foundry sync and the character-sheet widget's client fetch both
  use) — server is the authority; a widget hiding its own box client-side is
  never the fix, only a UX nicety on top (see the `data-is-gm`/`data-is-owner`
  mount attributes in `show_renderer_registry.go`).
- **Optimistic Concurrency:** `expected_updated_at` on update requests triggers
  409 Conflict if the entity was modified since that timestamp.

## Sidebar Navigation System

The entities plugin manages the sidebar drill panel — the slide-over
category view with its entity tree, folder nodes, favorites, and search.

### Dual-Parent Model

Entities have two mutually exclusive parent references:
- `parent_id` (CHAR(36) FK→entities) — parent is another entity
- `parent_node_id` (CHAR(36) FK→sidebar_nodes) — parent is a folder node

When one is set, the other must be NULL. The service layer enforces this
in `ReorderEntity()`. `static/js/sidebar_tree.js`'s tree builder resolves both.

### Sidebar Nodes (Pure Folders)

The `sidebar_nodes` table stores organizational folders that have NO entity
record. They appear only in the sidebar tree as non-navigable grouping
containers. CRUD via `/campaigns/:id/sidebar-nodes`.

**Footgun — folder nodes are keyed by the CATEGORY type, exact-match on reload.**
A node's `entity_type_id` must be the drilled category's own type (the sidebar
`?type=` param), because `SearchAPI` reloads nodes via `ListByType(campaignID,
typeID)` — an exact match. The drill listing rolls up sub-type entities
(`expandTypeIDsForListing`), so `results[0].EntityTypeID` can be a **sub-type**.
`sidebar_tree.js createGroupFolder` scopes a new empty folder from the tree
container's `data-entity-type-id`, so that attribute MUST be the category type,
not a per-row type — otherwise the node is created under a sub-type, never
returned on refresh, and the dropped entities are silently orphaned under an
invisible node (the "creating a folder does nothing" bug). `SidebarEntityList`
takes an explicit `typeID` and resolves the attribute via `sidebarTreeType()`
(prefers `typeID`; row/node fallback only when `typeID<=0`). Pinned by
`sidebar_list_test.go` + `sidebar_tree_reorder.test.mjs` (empty-folder cases).

### Favorites

The `entity_favorites` table stores per-user, per-campaign bookmarks.
API at `/campaigns/:id/entities/:eid/favorite` (toggle) and
`/campaigns/:id/favorites` (list).

### Tag Filtering

The search API accepts `?tags=slug1,slug2` for AND-logic tag filtering.
Uses a subquery with `HAVING COUNT(DISTINCT)` for correctness.

### Lazy Loading

Sidebar drill panel loads 50 entities per page. The template renders a
"Load more" sentinel when `total > len(results)`. JS IntersectionObserver
auto-triggers next-page fetches.

### Sidebar config model

The sidebar's structure is ONE stored model
(`campaigns.SidebarConfig.Items`) with ONE editor
(`static/js/sidebar_editor.js`, pencil-triggered inline edit).

## Business Rules

- Entity names must be non-empty (max 200 chars)
- Slug auto-generated from name, deduplicated with -2/-3 suffix, unique per campaign
- Entity type determines which fields appear in the profile and edit form
- Dynamic fields parsed from form params (field_<key>) by handler
- Private entities (is_private=true) filtered at SQL level: Players don't see them
- Show handler returns 404 (not 403) for private entities to avoid revealing existence
- FULLTEXT search on entity name (BOOLEAN MODE), LIKE fallback for queries < 4 chars
- Deleting an entity cascades via FK
- Default entity types seeded on campaign creation via EntityTypeSeeder interface
- 6 default types: Character, Location, Organization, Item, Note, Event

## Player Character Claiming

Links player-owned entities (typically characters) to campaign members, so
GMs can see who plays which character, reassign ownership, or unclaim.
Gated behind the `player-character-claiming` addon; existing campaigns
default to off.

- **`entity_types.claimable BOOLEAN NULL`** (migration 000029). NULL (unset)
  falls back to a legacy heuristic (`preset_category == "character"` or slug
  `*-character`); TRUE/FALSE is the Owner's explicit override
  (`isClaimableType`). Creating a player-character sub-type
  (`PresetCategory=="player_character"` or `slug=="player-character"`)
  requires the addon (`CreateEntityType` gates it via the injected
  `AddonChecker`) and defaults `claimable=true` when the addon is on.
- **UI surfaces**, all gated on `addon-enabled(player-character-claiming)` AND
  `isClaimableType(type)`:
  1. `claim_banner.templ` on the entity show page: "Claim this character"
     (Player+ action) when unclaimed, or "Claimed by &lt;name&gt;" (read-only)
     when `OwnerUserID != nil` — the Show handler resolves the id via
     `memberLister`, falling back to "a player" for a stale/unresolved owner.
  2. `category_owner_roster.templ`: Scribe+ owner overview on a claimable
     category dashboard — table of character + current owner + reassign
     select + unclaim button, capped at 100 entities/category. Both actions
     hit `PUT /campaigns/:id/entities/:eid/owner`.
  3. Per-type "Players can claim entities of this type" checkbox in the
     Customize hub and the Add-Category form, shown only when the addon is
     on; defaults to true when the addon is on.
- **Audit:** `entity.claimed` and `entity.owner_changed` actions in
  `internal/plugins/audit/model.go`, rendered in the activity feed with
  human-readable labels. `owner_changed` details include `new_owner_id`,
  `new_owner_name`, or `cleared: true`.
- **API:** `POST /campaigns/:id/entities/:eid/claim` (Player+) — idempotent
  if the caller already owns it; 409 if owned by someone else; 400 if the
  type isn't claimable. `PUT /campaigns/:id/entities/:eid/owner` (Scribe+) —
  body `{"owner_user_id": "user-uuid-or-null"}`; validates membership; no-op
  (200) if unchanged.
- **Design rationale:** see `.ai/decisions.md` ADR-039. The addon is
  owner-toggleable (existing campaigns don't get surprised), claimability is
  per-type (not every character-shaped type needs claiming), and both the
  dedicated "Player Character" sub-type and the legacy heuristic are
  supported so existing campaigns keep claiming on their "Character" type.

## Characters ("Cast") Page

`GET /campaigns/:id/characters` → `Handler.Characters` → `CharactersPage` /
`CharactersContent` (`characters.templ`). The campaign-wide "who's who".
Two addon-gated sections; the page 404s when neither addon is on:

- **Players section** (gated by the `player-character-claiming` addon,
  `view.ShowPlayers`) = every claimed player character. Sourced by
  `service.ListClaimed(campaignID, role, userID)` (`owner_user_id IS NOT NULL` +
  `visibilityFilter`) **unioned** with the viewer's own `ListByOwner` (unfiltered,
  so a player always sees their own PC even if private), de-duplicated and sorted
  viewer-first via the pure `assembleCastParty(...)` (unit-tested). The viewer's
  own cards get a "You" ribbon + accent ring.
- **NPCs/Monsters section** (gated by the `npcs` addon) = contributed by the npcs
  plugin, NOT built here. `entities` defines `NPCSectionProvider` (a `templ.Component`
  returned by `npcs.Handler.NPCSection`), injected via `SetNPCSectionProvider` in
  app wiring — so core never imports the addon. The npcs plugin renders a
  featured portrait row (entities tagged `CastTagSlug` = `cast`) above the
  full revealed list with the DM reveal/hide toggle. The standalone NPC
  gallery page (`GET /npcs`) redirects to `GET /campaigns/:id/characters`.
- **Cards** are real links to the entity page (work with no JS). The corner
  "quick look" button is progressively enhanced by `static/js/characters.js`
  (this plugin's own embedded static dir, served at
  `/static/plugins/entities/js/`) into the dynamic-surface frame's
  mini→full launch — an overlay that grows from the card
  (`Chronicle.surface.launch`) and lazy-loads the entity's `/preview` JSON.
  **It is mounted from the plugin body-script registry, NOT from
  `characters.templ`** (`internal/app/routes.go`'s `pluginBodyScripts` →
  `layouts.SetPluginBodyScripts` → `base.templ`). A `<script src>` inside the
  page templ would land inside `<main id="main-content">`, which every
  boosted sidebar navigation swaps, and htmx removes scripts from a swapped
  fragment (`allowScriptTags=false` in boot.js) — so mounting it from the
  page templ would wire the quick-look only on a direct URL load and
  silently do nothing through the sidebar (the cards still work as links, so
  the page would look identical). The registry emits after `{children...}`,
  outside the swapped region, so both paths deliver it; the module re-wires
  on `htmx:afterSettle` and returns immediately on pages with no
  `[data-cast-peek]`. Pinned by `characters_boosted_nav_test.go`; the ratchet
  is `tools/check-page-scripts.sh`.
- Nav: `sidebarCharactersLink` in `app.templ` (visible to every member).
- No migration (reuses `owner_user_id` + tags).

## `character_surface` block — the player-character "big widget"

The dynamic surface is a real layout block (`Type: "character_surface"`,
`Contexts: ["template"]`, `Singleton`), registered in `block_registry_core.go`.
It is the default page layout for player-character types:
`CreateEntityType` gives `isPlayerCharacterType(...)` types
`CharacterLayout()` (the surface block + permissions) instead of
`DefaultLayout()` (`service.go`, `model.go:CharacterLayout`). Because it's a
normal registered block, owners can customize it in the layout editor like
any other.

- **Server** (`character_surface.go`, `character_surface_block.templ`):
  `blockCharacterSurface` emits `<div data-widget="dynamic-surface">` with an
  inline `<script type="application/json" data-surface-schema>` built by
  `CharacterSurfaceSchemaJSON(entity, entityType, campaignID, csrf, canEdit)` —
  the entity's real data seeded, zero extra fetch. `json.Marshal`
  HTML-escapes it, so it's safe inside the script tag.
- **Client** (`static/js/widgets/character_surface.js`, loaded globally after
  `dynamic_surface.js`): registers the generic box renderers `char-header`
  (portrait + type), `char-attributes` (fields grouped by section), `char-entry`.
  A System (e.g. Draw Steel) can override these by re-registering the same names.
- **Security:** the description box does NOT inline `EntryHTML` (that would
  bypass role-aware secret stripping). It mounts the same `editor` widget the
  standard `entry` block uses (seeded endpoint + csrf + `canEdit`), so secrets
  and edit-gating are identical.
- **Auto-premake on addon enable:** `EnsurePlayerCharacterType(campaignID)`
  idempotently ensures one claimable player-character type exists nested
  under the default "Characters" category (`ParentTypeID` → the seeded
  `character` type). Three cases (matched by walking the campaign's types):
  (1) migrate a stray top-level PC type an earlier build premade, by
  re-parenting it (preserves claimed characters + layout); (2) nest a
  system's own character type (e.g. `drawsteel-character`, detected
  generically via `isClaimableType`, never by system name) — no rename, no
  field copy, since the type already carries the system's fields and its own
  slug renderer; (3) else create the generic "Player Characters" type
  (`CharacterLayout()` + claimable) nested, or top-level if no `character`
  category exists. Wired from `addons.EnableForCampaign` →
  `PresetApplier.ApplyAddonEnableEffects`, and replayed by the startup
  backfill (`internal/app/backfill.go`) — deploying heals production in
  place. The boot path only nests/creates; it never moves or deletes entity
  data. Tests: `ensure_pc_type_test.go`.
- **Owner-driven duplicate reconciliation (`MergeDuplicatePlayerCharacterType`):**
  because the boot path above is deliberately non-destructive, a campaign can
  end up with both a generic `player_character` type (holding the
  characters) and a system character type (e.g. `drawsteel-character`,
  empty) from enable-ordering. Migration `000030` auto-merges the
  unambiguous case on deploy and is retained permanently (it is applied in
  prod; deleting an applied migration crash-loops boot — see ADR-044). An
  additive, owner-triggered reconciliation handles what the migration skips
  (ambiguous `COUNT<>1`, or duplicates arising later), surfaced by the
  player-character SetupProvider on the extension settings page (see
  `addons/.ai.md` §"Setup Provider framework"). It classifies by
  `preset_category` + `slug`/`is_default` only (no system names), asserts
  exactly one source AND one target, and calls the repo's
  `MoveEntitiesAndDeleteType` (one tx: reassign `entity_type_id` so claims
  follow, then a `NOT EXISTS`-guarded DELETE of the emptied generic type —
  `entities.entity_type_id` is ON DELETE CASCADE, so emptying first is
  mandatory). Idempotent. Tests: `merge_duplicate_pc_test.go`,
  `pc_setup_snapshot_test.go`.
- **Field reconcile in place (`ReconcileEntityTypeFields`):** a system pack
  can declare new character fields (backstory, abilities…) after a campaign
  already created its type. The reconciler additively backfills: the pure
  `mergeNewFields` helper appends any declared field whose `Key` is absent
  (never removes, reorders, or overwrites, so a user-edited field wins and a
  second run adds nothing), then persists via `UpdateEntityType` (name
  unchanged, slug stable). `app/preset_applier.go`'s `ApplySystemPresets`
  drives it on package install/update. Type schema only, never entity data.
  Tests: `reconcile_fields_test.go`.
- **Single-owner duplicate guard (`CreateEntityType`):** Chronicle allows one
  type per preset-category, so the addon owns the player-character category.
  If an Owner manually requests a PC type and one already exists,
  `CreateEntityType` rejects it with a `Conflict`. This sits on top of the
  existing addon gate.

## Notes

- The entity profile page composes multiple widgets: title, editor, tags,
  attributes, relations. The page itself is a Templ template that provides mount points.
- Rich text editor (TipTap) is integrated via the editor widget with view/edit
  mode toggle. Entity show.templ mounts the widget with `data-widget="editor"`.
- Attributes widget mounts with `data-widget="attributes"` for inline field editing.
- Tags and relations widgets also mount on entity profile pages.
- **Footgun — entity_type reads share ONE scan path.** Every `entity_types`
  SELECT routes through the `entityTypeColumns` const + `scanEntityType(rowScanner)`
  helper in repository.go (FindByID/FindBySlug/ListByCampaign/ListChildTypes/
  ListByPresetCategory/ListAll). The scan binds *by position*, so adding a column
  means editing the const and the helper in exactly one place — never copy a
  bespoke SELECT/Scan pair back into a single method (that reintroduces
  scan-order drift, and a mismatch panics at runtime, not build).
  `TestEntityTypeRepository_Integration` (run via `make test-int`) is the live-DB
  guard that proves the column/scan order against a real MariaDB.
- **Footgun — every paginated read here MUST end its `ORDER BY` in `e.id`.**
  Neither `LIMIT/OFFSET` reader's leading sort column is unique (only
  `uq_entities_campaign_slug` is), so MariaDB's plan for tied rows is not
  stable across the statements of one walk — it uses a priority-queue sort
  while `LIMIT+OFFSET` is small and falls back to a full filesort once it is
  not. Measured on MariaDB 10.11 over 50,000 entities sharing one
  `updated_at`: a walk to exhaustion returned 50,000 rows but only 49,437
  distinct ones. The inheriting callers are the list page, the sync API's
  `ListEntities` and its pull loop, and both campaign-export
  walk-to-exhaustion loops. `pagination_total_order_test.go` walks every
  `LIMIT ? OFFSET ?` query in `repository.go` and requires a tiebreaker, so a
  new paginated read cannot land without one.
- **Footgun — a public-capable route must authorize the `:eid`, not just the
  campaign.** `GET /campaigns/:id/entities/:eid/backlinks` must carry the
  same campaign-match 404 + `CheckEntityAccess` that `Show`, `GetEntry`,
  `GetFieldsAPI`, `PreviewAPI` and `GetAliasesAPI` all carry, and
  `FindBacklinks` pins `e.campaign_id = ?` as its first predicate via the
  pure `backlinksWhere` builder, mirroring `visibilityFilter`.
  `AllowPublicCampaignAccess` + `RequireViewAccess` resolve and authorize the
  campaign and nothing about the entity id in the path; any new route under
  them must supply that term itself.
